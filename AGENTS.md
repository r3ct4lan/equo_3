# Разработка Equo

## Контекст и требования

- Начинайте с `docs/README.md` и `docs/product-context.md`.
- Нормативные требования: `docs/mvp-scope.md`, `docs/business-rules/business-rules.md`, `docs/api/http-contracts.md`, `docs/data-model/`, `docs/adr/architecture-decisions.md`, решения в `docs/open-questions.md`.
- Текущее состояние: `docs/product-context.md`; незавершённые задачи и зависимости: `docs/backlog.md`; итоговая приёмка и сведения о целевой среде: `docs/acceptance/`. Завершённые планы и промежуточные отчёты разработки сохранены в истории Git.
- Сообщения из переписки и handoff — предварительные сведения. Подтверждайте их кодом, тестами и Git; сохраняйте более свежие принятые требования. Не заменяйте нормативные документы восстановленными сокращениями.

## Самостоятельная работа над фичами

- MVP завершён. Для порученных задач бэклога владелец разрешил коммиты проверенных этапов и push накопительной ветки `codex/backlog`. Несколько задач выполняются подряд в ней; границу серии определяет владелец. После подготовки всей серии и успешного полного CI ветка сливается в `main` одним PR. Отдельное подтверждение каждого коммита и push не требуется. Разрешение не отменяет обязательные проверки и продуктовую приёмку.
- Краткие поручения вроде «какая следующая задача по бэклогу? давай сделай её» означают разрешение на полный цикл автономной разработки этой задачи: прочитайте актуальный бэклог и фактический статус, выберите следующую незавершённую задачу с учётом зависимостей и выполните декомпозицию, реализацию, точечные проверки, обновление документации, коммиты и push в `codex/backlog`. Технические решения принимайте самостоятельно в рамках принятых требований; подтверждение между этапами не запрашивайте.
- Самостоятельно декомпозируйте фичу на проверяемые этапы и выбирайте технические решения в рамках принятых требований и существующих границ модулей.
- Продолжайте с первого фактически незавершённого этапа, не реализуйте уже выполненное повторно. Сохраняйте стабильные ID требований и этапов; расхождения нумерации документируйте.
- Проверяйте каждый этап применимыми точечными тестами и проверками. Полный gate, включая browser E2E, запускайте только в GitHub Actions один раз после завершения серии задач на итоговом коммите накопительной ветки по `docs/quality-gate.md`.
- После каждого завершённого и проверенного этапа обновляйте соответствующую документацию и создавайте отдельный коммит. Задачи после MT-006 собирайте в ветке `codex/backlog`; MT-006 остаётся в отдельном PR. Не сливайте каждую следующую задачу отдельно в `main`. Обычные push и PR запускают быстрые CI-проверки. После успешного полного gate слейте накопленную ветку в `main` одним PR.
- Не запрашивайте подтверждение после каждого этапа при разрешённой автономной разработке. Обращайтесь к владельцу при существенном противоречии продуктовых требований или самостоятельно неустранимом блокере.
- Не отмечайте фичу завершённой по готовности одного слоя. Техническую приёмку отделяйте от решения Product Owner и готовности всего MVP.

## Проверка и сохранность

- Используйте WSL/Linux и Docker Compose из README. Локально запускайте только проверки затронутых частей; полные `make check`, `make check-full` и `make test-e2e` не запускайте. Завершите код, тесты и документацию до ручного запуска полного GitHub Actions gate на ветке `codex/backlog`. После запуска не добавляйте коммиты ради документации или мелких правок: успешный результат относится только к проверенному SHA. Если CI нашёл ошибку, исправьте её, локально проверьте затронутый участок и повторите полный CI на новом итоговом коммите. Не сливайте ветку, если `main` изменился после её синхронизации и проверки: сначала обновите ветку и повторите gate.
- Разрушающие тесты выполняйте только в изолированных test/E2E окружениях. Не переписывайте применённые миграции, dev-данные и volumes.
- Сохраняйте чужую незакоммиченную работу; добавляйте в коммит только относящиеся к этапу файлы.
- Domain не зависит от Symfony/Doctrine; Application не зависит от HTTP; адаптеры реализуют ports. Переиспользуйте API client, session coordination, cookie factory и email pipeline.
- Не раскрывайте refresh/CSRF/JWT, hashes, SQL и stack traces в публичных ответах, логах, UI и тестовых артефактах.
