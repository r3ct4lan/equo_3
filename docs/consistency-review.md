## 1. Цель и границы проверки

Проверка определяет, достаточно ли согласованы актуальные проектные артефакты для выбора первого вертикального среза. Рассмотрены терминология, роли, состояния, бизнес-операции, ограничения, модель хранения, HTTP-контракты и архитектурные решения.

Исходная E1-02 не проектировала недостающие механизмы и сохранила 13 доказательных замечаний. Владелец разрешил CONS-001, CONS-002 и CONS-004. При автономном закрытии Block A остальные десять замечаний разрешены по заданному приоритету источников и принципам безопасного, простого и обратимого решения; история каждого замечания сохранена.

Код приложения рассматривался только как дополнительное доказательство версии frontend-платформы и подготовленной инфраструктуры Messenger/RabbitMQ. Реализация приложения, миграции, определение границы MVP и выбор вертикального среза не входят в проверку.

Статусы связей:

- `Согласовано` — цепочка полна и не содержит обнаруженного расхождения;
- `Частично согласовано` — основные элементы присутствуют, но есть доказанный пробел или неоднозначность;
- `Отсутствует` — обязательное звено цепочки не зафиксировано;
- `Противоречие` — два актуальных источника задают несовместимые значения;
- `Не применимо` — звено не требуется для рассматриваемого понятия.

## 3. Краткое резюме

Основная доменная модель согласована: постоянный неориентированный `Connect`, агрегат `Debt`, текущий состав через `DebtParticipant`, автоматические и ручные `Transfer`, расчёт баланса, мягкое удаление, права чтения, оптимистическая версия и централизованная идемпотентность прослеживаются через все слои.

| Серьёзность | Всего | Открыто | Разрешено |

| Blocker | 0 | 0 | 0 |
| High | 3 | 0 | 3 |
| Medium | 8 | 0 | 8 |
| Low | 2 | 0 | 2 |
| **Итого** | **13** | **0** | **13** |

Открытых замечаний любого уровня не осталось.

Противоречие версии frontend, конкурентная выдача `UserActionToken`, надёжная доставка email, password policy, транзакционные границы, CHECK-ограничения, Debt-пример, DELETE-контракты, operational profile, invitation tokenHash, статус исторического отчёта и термин `relatedTransfer` синхронизированы. ADR-014 фиксирует нормативные TTL, retention, retry и rate limits. Блокеров для E1-04 нет.

## 5. Найденные замечания

<a id="cons-001"></a>

### CONS-001. Версия Nuxt противоречила принятому ADR — разрешено

- **Серьёзность:** High
- **Состояние:** Разрешено 2026-07-26
- **Тип:** противоречие
- **Затронутые артефакты:** корневой README, frontend package manifest, ADR-001
- **Источники:** [README, Repository structure](../README.md#repository-structure); [`frontend/package.json`](../frontend/package.json); [ADR-001](adr/architecture-decisions.md#adr-001-архитектура-mvp-как-модульный-монолит)
- **Исходное несоответствие:** на момент проверки ADR-001 принимал Nuxt 3, тогда как README и package manifest фиксировали Nuxt 4.5.
- **Исходное влияние на разработку:** разные исполнители могли выбрать несовместимую версию frontend-платформы, структуру модулей и набор зависимостей.
- **Решение:** ADR-001 обновлён и теперь принимает Nuxt 4.5 для web-клиента.
- **Остаточное влияние:** отсутствует; версия платформы согласована между ADR, README и package manifest.
- **Вопрос:** закрыт.
- **Рекомендуемый владелец:** Maksim Smolkov как владелец комплекта ADR.

<a id="cons-002"></a>

### CONS-002. Конкурентная выдача UserActionToken не защищала правило аннулирования — разрешено

- **Серьёзность:** High
- **Состояние:** Разрешено 2026-07-27
- **Тип:** пробел
- **Затронутые артефакты:** бизнес-правила, модель сущностей, ER, HTTP, ADR-007
- **Источники:** [BR-SEC-004](business-rules/business-rules.md#br-sec-004-аннулирование); [`UserActionToken`, инварианты и выдача](data-model/entities.md#10-useractiontoken); [ER, уникальность `UserActionToken`](data-model/er-diagram.md#useractiontoken); [общие правила HTTP](api/http-contracts.md#80-общие-правила-выдачи-useractiontoken); [ADR-007](adr/architecture-decisions.md#adr-007-унифицированные-одноразовые-токены)

### CONS-004. Отсутствовало решение о надёжной доставке email — разрешено

## 6. Полностью согласованные области

- Модель постоянного неориентированного `Connect`, канонический порядок пары и запрет удаления.
- Роли автора, плательщика и текущего участника долга, включая неизменяемость плательщика и управление только автором.
- Представление `includePayerInSplit` через наличие текущего `DebtParticipant`, без отдельного поля `Debt`.
- `Transfer` как единственный источник истины для баланса; направления, знак баланса и разрешённая переплата.
- Автоматический `DEBT_SHARE`, отсутствие self-transfer плательщика и управление только через агрегат долга.
- Мягкое удаление финансовых сущностей, сохранение истории и недоступность удалённых записей для активного поведения.
- Правила видимости Connect, Transfer и Debt, скрытие недоступного долга в `debtReference`, отсутствие чужого email.
- Оптимистическая блокировка `Debt`/`Transfer` через `version`, `ETag`, `If-Match`, `428` и `409 VERSION_CONFLICT`.
- Структура централизованной идемпотентности: scope, operation, key, request hash, повтор результата и конфликт повторного ключа с другим телом.
- Единая валюта EUR, целые евроценты, UUID, серверный `createdAt`, RFC 3339 UTC и отсутствие пользовательской даты финансовой операции.
- Разделение ответственности между локальными ограничениями PostgreSQL и межтабличными инвариантами доменного слоя.
