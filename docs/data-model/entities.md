## Назначение

**Статус:** финальная согласованная версия этапа проектирования.


Документ фиксирует состав сущностей Equo, назначение полей, связи, ограничения целостности и правила жизненного цикла.

Это не готовая SQL-схема. Точные типы PostgreSQL, имена индексов и миграций будут определены отдельно.

Общие соглашения:

- идентификаторы бизнес-сущностей — UUID;
- даты создаются сервером и хранятся как PostgreSQL `timestamptz`;
- деньги хранятся в целых евроцентах;
- валюта MVP — EUR;
- денежные значения не используют типы с плавающей точкой;
- финансовые записи не удаляются физически;
- изменения агрегата долга выполняются транзакционно.

# 1. User

## Назначение

Аккаунт пользователя Equo.

## Поля

| Поле | Обязательно | Назначение |
|---|---:|---|
| `id` | да | UUID |
| `name` | да | Отображаемое имя |
| `email` | да | Основной email и логин |
| `passwordHash` | да | Хэш пароля |
| `isActive` | да | Доступность аккаунта |
| `createdAt` | да | Дата регистрации |

## Состояния

`isActive = false` означает:

1. аккаунт зарегистрирован, но не активирован;
2. пользователь самостоятельно деактивировал аккаунт.

В обоих случаях запрещены вход и новые операции. Существующие финансовые данные сохраняются.

## Инварианты

- email перед сохранением нормализуется: обрезаются пробелы по краям, значение приводится к нижнему регистру;
- уникальный индекс создаётся по сохранённому нормализованному `email`;
- пароль хранится только как хэш Symfony PasswordHasher с алгоритмом `auto`; открытый пароль не сохраняется;
- `createdAt` неизменяем;
- пользователь не удаляется физически в MVP.

## Нормализация email

- удалить пробелы по краям;
- привести к нижнему регистру для поиска;
- не удалять точки;
- не удалять `+suffix`;
- не применять правила конкретных провайдеров.

## Связи

Пользователь может быть:

- стороной множества `Connect`;
- автором и плательщиком множества `Debt`;
- участником множества `DebtParticipant`;
- отправителем, получателем и автором `Transfer`;
- владельцем `UserSession`;
- владельцем `UserActionToken`;
- автором `ConnectInvitation`.

# 2. Connect

## Назначение

Постоянная неориентированная связь двух пользователей.

## Поля

| Поле | Обязательно | Назначение |
|---|---:|---|
| `id` | да | UUID |
| `firstUserId` | да | Первая сторона |
| `secondUserId` | да | Вторая сторона |
| `createdAt` | да | Дата создания |

## Инварианты

- стороны различны;
- для одной неупорядоченной пары существует один коннект;
- порядок пользователей не имеет бизнес-смысла;
- коннект не удаляется и не деактивируется.

## Канонический порядок

Рекомендуется сохранять пару в стабильном порядке:

`firstUserId < secondUserId`

Тогда возможен обычный индекс:

`UNIQUE(firstUserId, secondUserId)`

## Создание

Коннект создаётся:

- при принятии приглашения;
- автоматически для доли долга;
- вручную между активными участниками общего доступного долга.

Создание идемпотентно: существующий коннект возвращается повторно.

## Неактивная сторона

Если одна сторона деактивирована:

- коннект остаётся в списке;
- история и баланс доступны;
- новые долги и трансферы запрещены;
- после реактивации ограничения снимаются.

# 3. ConnectInvitation

## Назначение

Одноразовая ссылка для создания коннекта.

## Поля

| Поле | Обязательно | Назначение |
|---|---:|---|
| `id` | да | UUID |
| `createdById` | да | Автор |
| `tokenHash` | да | Хэш публичного токена |
| `createdAt` | да | Дата создания |
| `expiresAt` | да | Срок действия |
| `usedAt` | нет | Дата использования |
| `acceptedById` | нет | Принявший пользователь |

## Инварианты

- открытый токен не хранится;
- `tokenHash` уникален;
- собственное приглашение принять нельзя;
- обе стороны должны быть активны;
- истёкший токен недействителен;
- использованный токен принимается повторно только тем же `acceptedById`, которому возвращается существующий `Connect`;
- для другого пользователя использованный токен недействителен;
- существующий `Connect` возвращается без создания дубля;
- повторная обработка не создаёт второй коннект.

## Единственное активное приглашение

Для пользователя не более одного действующего неиспользованного приглашения.

Повторный запрос:

- возвращает существующее;
- создаёт новое после истечения или использования;
- не продлевает срок старого;
- не поддерживает отзыв в MVP.

## Формат публичного токена

Токен имеет вид `<invitationId>.<HMAC-signature>`. В базе хранится `tokenHash` полного токена. Новые приглашения подписываются активным ключом. Для повторного формирования существующей ссылки сервер перебирает активный и совместимые старые ключи до совпадения вычисленного хэша с `tokenHash`.

## Конкурентность

Получение или создание приглашения сериализуется блокировкой строки автора (`User`) либо PostgreSQL advisory lock, поскольку при отсутствии приглашения блокировать его строку невозможно. Принятие выполняется транзакционно с блокировкой приглашения. Уникальность пары в `Connect` дополнительно защищает от дублей.

# 4. Debt

## Назначение

Корень агрегата группового расхода.

## Поля

| Поле | Обязательно | Назначение |
|---|---:|---|
| `id` | да | UUID |
| `title` | да | Название |
| `description` | нет | Описание |
| `totalAmount` | да | Сумма в евроцентах |
| `payerId` | да | Плательщик |
| `createdById` | да | Автор |
| `createdAt` | да | Дата создания |
| `isDeleted` | да | Мягкое удаление |
| `version` | да | Оптимистическая версия |

## Инварианты

- `totalAmount > 0`;
- ровно один плательщик;
- плательщик неизменяем;
- автор — плательщик или участник;
- есть хотя бы один участник, отличный от плательщика;
- новые участники и плательщик активны;
- `version` начинается с `1`;
- изменение и удаление увеличивают версию;
- удалённый долг не восстанавливается.

## Доступность нового плательщика и участника

Пользователь может быть выбран в новой финансовой команде, если он активен и является:

- текущим пользователем;
- стороной существующего `Connect` текущего пользователя;
- текущим соучастником доступного текущему пользователю долга.

Общий поиск произвольных пользователей отсутствует.

## Автор и плательщик

Автор и плательщик могут различаться.

Если автор не плательщик:

- он обязан участвовать в разделении;
- он не может удалить себя из состава.

Если плательщик входит в разделение:

- он учитывается в расчёте;
- self-transfer не создаётся.

## Редактирование

Редактирует только автор, если:

- долг не удалён;
- автор активен;
- плательщик активен;
- версия совпадает;
- итоговый состав валиден.

Неактивного обычного участника можно оставить или удалить. Добавить или восстановить его нельзя до реактивации.

## Удаление

Мягкое:

`isDeleted = true`

Все связанные активные `DEBT_SHARE` перестают влиять на баланс. Ручные трансферы не изменяются.

## Чтение

Активный долг доступен:

- автору;
- плательщику;
- текущим участникам.

Удалённый из состава пользователь теряет доступ к долгу, но видит свои трансферы.

Удалённый долг:

- не отображается в списке;
- не имеет отдельного архива;
- доступен по прямой ссылке или из трансфера;
- только для чтения;
- доступен автору, плательщику и составу на момент удаления.

## Версия агрегата

`Debt.version` защищает согласованное состояние:

- самого долга;
- `DebtParticipant`;
- автоматических `DEBT_SHARE`;
- рассчитанных сумм.

# 5. DebtParticipant

## Назначение

Связь пользователя с долгом.

## Поля

| Поле | Обязательно | Назначение |
|---|---:|---|
| `id` | да | UUID |
| `debtId` | да | Долг |
| `userId` | да | Пользователь |
| `createdAt` | да | Дата первого добавления |
| `isDeleted` | да | Исключён ли из состава |

## Инварианты

- `(debtId, userId)` уникальна, включая удалённые записи;
- текущий участник имеет `isDeleted = false`;
- удалённый участник имеет `isDeleted = true`;
- запись может быть восстановлена;
- восстановление разрешено только активному пользователю;
- `createdAt` не меняется при восстановлении.

## Связь с долей

Для каждого текущего участника (`DebtParticipant.isDeleted = false`), кроме плательщика, существует один `DEBT_SHARE`. Текущий участник может иметь неактивный аккаунт, если деактивировался после добавления.

Рекомендуемая связь:

- `Transfer.debtParticipantId → DebtParticipant.id`;
- не более одного `DEBT_SHARE` на `DebtParticipant`.

Для плательщика запись участия может быть, а трансфера самому себе нет.

## Исключение

При исключении:

- `DebtParticipant.isDeleted = true`;
- его `DEBT_SHARE.isDeleted = true`;
- доступ пользователя к долгу прекращается;
- выполняется полный пересчёт;
- версия долга увеличивается.

## Повторное добавление

При повторном добавлении активного пользователя:

- восстанавливается прежний `DebtParticipant`;
- восстанавливается прежний `DEBT_SHARE`;
- сумма пересчитывается;
- дубли не создаются.

# 6. Transfer

## Назначение

Единственная сущность, непосредственно влияющая на баланс.

## Поля

| Поле | Обязательно | Назначение |
|---|---:|---|
| `id` | да | UUID |
| `connectId` | да | Коннект |
| `senderId` | да | Отправитель |
| `receiverId` | да | Получатель |
| `amount` | да | Сумма в евроцентах |
| `type` | да | `DEBT_SHARE` или `MANUAL` |
| `createdById` | нет | Автор ручного трансфера; для `DEBT_SHARE` равно `null` |
| `createdAt` | да | Дата создания |
| `isDeleted` | да | Мягкое удаление |
| `version` | да | Оптимистическая версия |
| `debtId` | нет | Долг для `DEBT_SHARE` |
| `debtParticipantId` | нет | Участник для `DEBT_SHARE` |
| `relatedTransferId` | нет | Ссылка `MANUAL` на `DEBT_SHARE` |

## Общие инварианты

- `amount > 0`;
- отправитель и получатель различны;
- обе стороны принадлежат `connectId`;
- `version >= 1`;
- только `isDeleted = false` влияет на баланс;
- `createdAt` неизменяем;
- валюта подразумевается как EUR.

## Тип `DEBT_SHARE`

- создаётся только через команды долга;
- направление: плательщик → участник;
- `createdById = null`;
- `debtId` обязателен;
- `debtParticipantId` обязателен;
- `relatedTransferId` пуст;
- напрямую не редактируется;
- защищён версией `Debt`;
- для плательщика не создаётся;
- удаляется и восстанавливается только вместе с долгом или участием.

## Тип `MANUAL`

- создаётся активной стороной коннекта;
- автор является отправителем или получателем;
- `debtId` и `debtParticipantId` пусты;
- `relatedTransferId` необязателен;
- редактируется и удаляется только автором;
- обе стороны должны быть активны для изменения;
- переплата разрешена;
- после удаления не восстанавливается.

## `relatedTransferId`

Если заполнен:

- исходный трансфер — `MANUAL`;
- целевой — `DEBT_SHARE`;
- оба относятся к одному `Connect`;
- при установке или замене ссылки целевой трансфер не удалён;
- при редактировании других полей прежняя неизменённая ссылка может сохраняться, даже если цель позднее удалена;
- связь можно очистить;
- связь не влияет на баланс и статус погашения.

После удаления долга или доли историческая ссылка сохраняется как историческая.

## Версия трансфера

`version` увеличивается при фактическом изменении суммы, направления, `relatedTransferId`, `isDeleted` или при восстановлении `DEBT_SHARE`. Для автоматического трансфера пользовательская конкуренция контролируется `Debt.version`.

## Удаление ручного трансфера

- `isDeleted = true`;
- `version += 1`;
- исключение из баланса;
- сохранение в истории;
- дальнейшее редактирование запрещено.

## Изменение направления

Допустима только перестановка двух сторон существующего коннекта. Третьего пользователя добавить нельзя.

# 7. Расчёт долей

## Входные данные

- `Debt.totalAmount`;
- текущие `DebtParticipant` с `isDeleted = false`.

Отдельное поле `includePayerInSplit` в `Debt` не хранится. Оно вычисляется по наличию текущего `DebtParticipant` плательщика:

`includePayerInSplit = exists DebtParticipant(debtId, payerId, isDeleted = false)`

В HTTP-командах признак может передаваться для удобства клиента, но сервер преобразует его в создание, восстановление или мягкое удаление соответствующего `DebtParticipant`.

## Формула

`shareAmount = ceil(totalAmount / participantCount)`

`participantCount` — число текущих `DebtParticipant` с `isDeleted = false`, включая плательщика, если он участвует. `User.isActive` не влияет на включение уже текущего участника в расчёт.

## Генерация трансферов

Для каждого текущего участника, кроме плательщика:

1. найти или создать `Connect`;
2. создать или восстановить `DEBT_SHARE`;
3. `senderId = payerId`;
4. `receiverId = participant.userId`;
5. `amount = shareAmount`.

## Полный пересчёт

Изменение суммы, состава или включения плательщика пересчитывает все активные доли.

---

# 8. Расчёт баланса

Для коннекта пользователей `A` и `B`:

`balance(A, B) = Σ active(A → B) - Σ active(B → A)`

- `> 0`: `B` должен `A`;
- `< 0`: `A` должен `B`;
- `= 0`: баланс нулевой.

Баланс лучше не хранить как источник истины. Допустимы кэш или read-модель, полностью восстанавливаемые из `Transfer`.

# 9. UserSession

## Назначение

Серверное состояние refresh-сессии.

## Поля

| Поле | Обязательно | Назначение |
|---|---:|---|
| `id` | да | UUID |
| `userId` | да | Владелец |
| `refreshTokenHash` | да | Хэш refresh-токена |
| `createdAt` | да | Дата создания |
| `expiresAt` | да | Срок действия |
| `revokedAt` | нет | Дата отзыва |

## Инварианты

- открытый refresh-токен не хранится;
- отозванная или истёкшая сессия недействительна;
- refresh-токен ротируется;
- старый токен повторно не принимается;

- уже выданные access-токены могут действовать до короткого `exp`;
- защищённые команды дополнительно проверяют `User.isActive`, поэтому деактивация действует немедленно;
- refresh выполняется с блокировкой строки сессии и атомарной заменой хэша.

# 10. UserActionToken

## Назначение

Единая сущность email-подтверждений.

## Поля

| Поле | Обязательно | Назначение |
|---|---:|---|
| `id` | да | UUID |
| `userId` | да | Владелец |
| `tokenHash` | да | Хэш токена |
| `purpose` | да | Назначение |
| `payload` | нет | Дополнительные данные |
| `createdAt` | да | Дата создания |
| `expiresAt` | да | Срок действия |
| `usedAt` | нет | Дата успешного использования |
| `invalidatedAt` | нет | Дата аннулирования без использования |

## `purpose`

- `ACTIVATE_ACCOUNT`
- `RESET_PASSWORD`
- `CHANGE_EMAIL`

## `payload`

Для активации и сброса пароля:

`null`

Для смены email:

```json
{
  "newEmail": "new@example.com"
}
```

## Инварианты

- публичный токен имеет формат
  `<keyVersion>.<base64url(32 cryptographically random bytes)>`;
- в базе хранится только versioned digest
  `<keyVersion>:<base64url(HMAC-SHA-256(key, publicToken))>` по ADR-016;
- `tokenHash` уникален;
- токен действует только для своего назначения;
- токен одноразовый;
- истёкший токен недействителен;
- действие и `usedAt` сохраняются атомарно;
- `usedAt` и `invalidatedAt` не могут быть заполнены одновременно;
- для одного `(userId, purpose)` существует не более одного незавершённого токена с `usedAt IS NULL` и `invalidatedAt IS NULL`;
- выдача сериализуется транзакционной блокировкой строки `User`;
- новый запрос аннулирует все прежние незавершённые токены того же назначения, включая истёкшие, через `invalidatedAt`;
- новый email повторно проверяется на уникальность при подтверждении.

## Активация

`ACTIVATE_ACCOUNT` используется после регистрации и деактивации.

Результат:

`User.isActive = true`

Сессия автоматически не создаётся.

## Сброс пароля

Новый пароль приходит в команде, а не хранится в `payload`.

Сброс:

- меняет `passwordHash`;
- отзывает все refresh-сессии;
- уже выданный access-токен может действовать до короткого `exp`;
- не меняет `isActive`.

# 11. IdempotencyRecord

## Назначение

Защита команд создания от повторной обработки.

## Рекомендуемые поля

| Поле | Обязательно | Назначение |
|---|---:|---|
| `id` | да | UUID |
| `scope` | да | Пространство уникальности запроса |
| `userId` | нет | Связанный пользователь; пусто для регистрации |
| `operation` | да | Тип команды |
| `idempotencyKey` | да | Клиентский ключ |
| `requestHash` | да | Хэш нормализованного запроса |
| `responseStatus` | нет | HTTP-статус результата |
| `responseBody` | нет | Сохранённый результат или ссылка |
| `createdAt` | да | Дата |
| `expiresAt` | да | Окончание 24-часового срока хранения |

## Уникальность

`UNIQUE(scope, operation, idempotencyKey)`

Примеры `scope`:

- авторизованная команда: `user:<userId>`;
- регистрация: `public`.

`userId` хранится дополнительно для навигации и аудита, но не является частью уникального ключа.

## Поведение

- новая транзакция резервирует запись с `responseStatus = null`;
- конкурентная транзакция с тем же ключом ждёт завершения уникальной вставки либо читает сохранённый результат;
- новый ключ — команда выполняется;
- тот же ключ и тело — возвращается исходный результат;
- тот же ключ и другое тело — конфликт;
- бизнес-уникальность всё равно защищается отдельными индексами;
- гарантия идемпотентности действует до физической очистки записи по конфигурируемому сроку хранения.

# 12. EmailDeliveryOutbox

## Назначение

Надёжно зафиксировать намерение отправить email, связанный с `UserActionToken`, в той же транзакции PostgreSQL, что и бизнес-изменение.

## Поля

| Поле | Обязательно | Назначение |
|---|---:|---|
| `id` | да | UUID и стабильный `deliveryId` для дедупликации |
| `userActionTokenId` | да | Связанный `UserActionToken` |
| `recipientEmail` | да | Нормализованный адрес получателя |
| `templateKey` | да | Ключ шаблона для purpose токена |
| `encryptedPayload` | нет | Зашифрованный токен или готовая ссылка и переменные шаблона |
| `status` | да | `PENDING`, `PUBLISHED`, `SENT` или `FAILED` |
| `createdAt` | да | Дата создания задания |
| `availableAt` | да | Не отправлять в RabbitMQ раньше этого времени |
| `publishedAt` | нет | Время подтверждённой публикации в RabbitMQ |
| `sentAt` | нет | Время успешной передачи письма Symfony Mailer |
| `failedAt` | нет | Время окончательного отказа |
| `publishAttempts` | да | Количество попыток публикации relay |
| `lastError` | нет | Безопасное диагностическое описание без токена и ciphertext |

## Инварианты

- для одного `UserActionToken` существует не более одного задания доставки;
- новая запись создаётся в состоянии `PENDING`;
- `PUBLISHED` устанавливается только после publisher confirm RabbitMQ;
- `SENT` и `FAILED` являются взаимоисключающими конечными состояниями;
- `encryptedPayload` обязателен до отправки и очищается после `SENT`, `FAILED` или истечения токена;
- `recipientEmail`, `templateKey` и purpose связанного токена согласуются прикладным слоем;
- открытый токен, ссылка и ciphertext не попадают в логи;
- удаление outbox выполняется раньше физического удаления связанного токена.

## Жизненный цикл

```text
PENDING → PUBLISHED → SENT
                   ↘ FAILED
```

Relay может повторно опубликовать одно задание после сбоя между publisher confirm и фиксацией `PUBLISHED`. Consumer использует `id` как ключ дедупликации и повторно проверяет актуальность `UserActionToken`.

# 13. Карта связей

## User — Connect

- `User` участвует во многих `Connect`;
- `Connect` содержит ровно двух пользователей.

## User — Debt

- пользователь создаёт много долгов;
- пользователь может быть плательщиком многих долгов;
- долг имеет одного автора и одного плательщика.

## Debt — DebtParticipant

- долг имеет много участников;
- участие относится к одному долгу и пользователю;
- `(debtId, userId)` уникальна.

## Debt — Transfer

- один долг имеет один или несколько `DEBT_SHARE`;
- `MANUAL` не ссылается на `Debt` напрямую.

## DebtParticipant — Transfer

- текущий участник, кроме плательщика, имеет один `DEBT_SHARE`;
- участник-плательщик self-transfer не имеет;
- связь сохраняется при мягком удалении.

## Connect — Transfer

- коннект имеет много трансферов;
- трансфер относится к одному коннекту;
- его стороны совпадают со сторонами коннекта.

## Transfer — Transfer

- `MANUAL` может ссылаться на один `DEBT_SHARE`;
- один `DEBT_SHARE` может иметь несколько связанных ручных трансферов.

## User — UserSession

Один пользователь имеет много сессий.

## User — UserActionToken

Один пользователь имеет много токенов действий.

## UserActionToken — EmailDeliveryOutbox

Один токен имеет 0..1 задание доставки; каждое задание относится ровно к одному токену.

# 14. Рекомендуемые ограничения БД

Для MVP этот перечень нормативен. Раздел локальных CHECK-ограничений ER-описания обязан повторять его полностью; Mermaid-, DOT-, SVG- и PNG-представления являются обзорными и не заменяют этот перечень.

## User

- unique index по нормализованному email;
- `CHECK(length(btrim(email)) > 0)`;
- `CHECK(length(btrim(name)) > 0)`.

## Connect

- `CHECK(firstUserId <> secondUserId)`;
- канонический порядок пары;
- `UNIQUE(firstUserId, secondUserId)`.

## ConnectInvitation

- `UNIQUE(tokenHash)`;
- `CHECK((usedAt IS NULL) = (acceptedById IS NULL))`;
- `CHECK(expiresAt > createdAt)`;
- индекс по автору, сроку и использованию.

## Debt

- `CHECK(totalAmount > 0)`;
- `CHECK(version >= 1)`;
- `CHECK(length(btrim(title)) > 0)`;
- индексы по автору, плательщику и удалению.

## DebtParticipant

- `UNIQUE(debtId, userId)`;
- индексы по пользователю и активному составу.

## Transfer

- `CHECK(amount > 0)`;
- `CHECK(senderId <> receiverId)`;
- `CHECK(version >= 1)`;
- enum/check для `type`;
- unique constraint на один `DEBT_SHARE` для `debtParticipantId`;
- индексы по коннекту, сторонам, долгу, связи и удалению.

Соответствие сторон трансфера сторонам коннекта проверяется доменным слоем внутри транзакции. Пользовательские триггеры не применяются.

## UserSession

- `UNIQUE(refreshTokenHash)`;
- `CHECK(expiresAt > createdAt)`;
- индексы по пользователю, сроку и отзыву.

## UserActionToken

- `UNIQUE(tokenHash)`;
- частичный `UNIQUE(userId, purpose) WHERE usedAt IS NULL AND invalidatedAt IS NULL`;
- enum/check для `purpose`;
- `CHECK(expiresAt > createdAt)`;
- `CHECK(NOT (usedAt IS NOT NULL AND invalidatedAt IS NOT NULL))`;
- индексы по пользователю, назначению, сроку и использованию.

## IdempotencyRecord

- `UNIQUE(scope, operation, idempotencyKey)`;
- `CHECK(expiresAt > createdAt)`;
- очистка по `expiresAt`.

## EmailDeliveryOutbox

- `UNIQUE(userActionTokenId)`;
- enum/check для `status`;
- `CHECK(publishAttempts >= 0)`;
- `CHECK(availableAt >= createdAt)`;
- `CHECK(NOT (sentAt IS NOT NULL AND failedAt IS NOT NULL))`;
- частичный индекс по `(availableAt, createdAt)` для `status = 'PENDING'`;
- индексы по статусу, `publishedAt`, `sentAt` и `failedAt`.

# 15. Транзакционные границы

## Создание долга

Одна транзакция:

1. `Debt`;
2. `DebtParticipant`;
3. нужные `Connect`;
4. расчёт долей;
5. `DEBT_SHARE`;
6. идемпотентный результат.

## Изменение долга

Одна транзакция:

1. проверка версии;
2. обновление долга;
3. сравнение состава;
4. создание, удаление или восстановление участников;
5. создание коннектов;
6. полный пересчёт долей;
7. увеличение версии.

## Удаление долга

Одна транзакция:

1. права и версия;
2. `Debt.isDeleted = true`;
3. исключение `DEBT_SHARE`;
4. увеличение версии.

## Принятие приглашения

Одна транзакция:

1. проверка и блокировка приглашения;
2. поиск или создание `Connect`;
3. заполнение `usedAt` и `acceptedById`.

## Использование UserActionToken

Одна транзакция:

1. поиск по хэшу;
2. проверка назначения и срока;
3. выполнение действия;
4. установка `usedAt`;
5. аннулирование конкурирующих токенов при необходимости.

## Деактивация аккаунта

Одна транзакция:

1. блокировка `User` через `SELECT FOR UPDATE`;
2. проверка текущего пароля;
3. установка `User.isActive = false`;
4. установка `revokedAt` всем незавершённым `UserSession` пользователя.

## Смена пароля

Одна транзакция:

1. блокировка `User` через `SELECT FOR UPDATE`;
2. проверка текущего пароля;
3. обновление `User.passwordHash`;
4. установка `revokedAt` всем незавершённым `UserSession`, включая текущую.

## Сброс пароля

Одна транзакция:

1. блокировка `User` и `UserActionToken` через `SELECT FOR UPDATE`;
2. проверка purpose, срока, `usedAt` и `invalidatedAt`;
3. обновление `User.passwordHash`;
4. установка `UserActionToken.usedAt`;
5. установка `revokedAt` всем незавершённым `UserSession`.

## Выдача UserActionToken

Одна транзакция:

1. блокировка строки `User` через `SELECT FOR UPDATE`;
2. установка `invalidatedAt` всем прежним строкам того же `(userId, purpose)` с `usedAt IS NULL` и `invalidatedAt IS NULL`, включая истёкшие;
3. создание нового `UserActionToken`;
4. создание связанного `EmailDeliveryOutbox` в состоянии `PENDING`.

Частичный уникальный индекс остаётся последней защитой от конкурентного дубля. Для первичной регистрации новая строка `User`, первый `ACTIVATE_ACCOUNT` и задание доставки создаются в одной транзакции; уникальность нормализованного email защищает конкурентную регистрацию.

## Публикация EmailDeliveryOutbox

Короткая транзакция relay:

1. блокировка готовых строк `PENDING` через `FOR UPDATE SKIP LOCKED`;
2. увеличение `publishAttempts` и публикация durable persistent message `SendUserActionEmail` в RabbitMQ;
3. ожидание publisher confirm;
4. установка `PUBLISHED` и `publishedAt`.

При ошибке публикации запись остаётся `PENDING`, получает безопасный `lastError`, а следующая попытка планируется через `availableAt`: начальная задержка 30 секунд, множитель 2, максимум 30 минут. Relay продолжает попытки, пока связанный токен действителен; после его истечения запись получает `FAILED`. Сообщение содержит только `deliveryId` и несекретные routing-метаданные; `encryptedPayload` остаётся в PostgreSQL.

## Обработка SendUserActionEmail

Consumer Messenger:

1. блокирует outbox через `SELECT FOR UPDATE` и загружает токен по `deliveryId`;
2. пропускает завершённое задание;
3. проверяет, что токен текущий, не использован, не аннулирован и не истёк; иначе устанавливает `FAILED`/`failedAt`, очищает payload и завершает сообщение без retry;
4. расшифровывает payload только в памяти;
5. отправляет письмо через выделенный синхронный transport Symfony Mailer без повторной постановки `SendEmailMessage` в Messenger;
6. устанавливает `SENT`, `sentAt` и очищает `encryptedPayload`.

После первой неудачной SMTP-попытки consumer выполняет не более пяти повторов с задержками 1 минута, 5 минут, 15 минут, 1 час и 6 часов. После исчерпания retry сообщение попадает в failure transport, а запись переводится в `FAILED` без сохранения секрета в `lastError`.

Повтор после окончательного отказа создаёт новый `UserActionToken` и новый outbox; запись `FAILED` не переиспользуется.

# 17. Зафиксированные решения перед ER-диаграммой и SQL-схемой

## Участие плательщика в разделении

Отдельное поле `includePayerInSplit` в `Debt` не хранится. Участие плательщика определяется по активному `DebtParticipant` с `userId = payerId`.

## Автор автоматического трансфера

Для `DEBT_SHARE` поле `Transfer.createdById` равно `null`. Автоматический трансфер создаётся системой, а его источник определяется через `debtId`, `debtParticipantId` и `type`.

## Состав удалённого долга

Отдельный snapshot не создаётся. После мягкого удаления `Debt` и его состав больше не изменяются. Активные `DebtParticipant` фиксируют состав на момент удаления, а ранее исключённые участники остаются с `isDeleted = true`.

## Сроки хранения инфраструктурных записей

Нормативный профиль MVP:

- логическое окно `IdempotencyRecord` — ровно 24 часа с первого запроса; `expiresAt = createdAt + 24 hours`, физическая очистка допускается после него;
- использованные, аннулированные и истёкшие `UserActionToken` — 30 дней после конечного события или `expiresAt`;
- отозванные и истёкшие `UserSession` — 30 дней после `revokedAt` или `expiresAt`;
- использованные и истёкшие `ConnectInvitation` — 30 дней после `usedAt` или `expiresAt`;
- завершённые `EmailDeliveryOutbox` — 30 дней после `sentAt` или `failedAt`.

Срок действия refresh-сессии — 30 дней; `ACTIVATE_ACCOUNT` — 24 часа; `RESET_PASSWORD` и `CHANGE_EMAIL` — 30 минут; `ConnectInvitation` — 7 дней. Физическая очистка выполняется фоновым заданием только после наступления соответствующей точки.

Очистка выполняется фоновым заданием. Активные записи до истечения срока действия не удаляются.

## Идемпотентность

`IdempotencyRecord` остаётся единым инфраструктурным механизмом защиты команд создания от повторной обработки запросов.

## Защита инвариантов в PostgreSQL

На уровне базы используются:

- внешние ключи;
- `NOT NULL`;
- `CHECK`;
- `UNIQUE`;
- частичные уникальные индексы.

Межтабличные бизнес-инварианты проверяются доменным слоем внутри транзакций. Пользовательские PostgreSQL-триггеры для дублирования бизнес-логики в MVP не применяются.
