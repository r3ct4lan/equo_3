## 2. Правила ведения

1. Идентификатор `OQ-*` назначается один раз, не переиспользуется и не перенумеровывается.
2. Основная карточка содержит все источники; повторное упоминание сохраняется как `Merged`.
3. Решение считается закрытым только после синхронизации нормативных документов, фиксации даты и автора.
4. Пересмотр решения не удаляет историю: карточка дополняется новым решением и ссылками на изменённые документы.
5. Контрольная точка закрытого вопроса считается выполненной.

- **Почему требовалось решение:** проверка и аннулирование без сериализации допускали два действующих токена.

- **Возможные варианты:** блокировка `User`, advisory lock либо иной механизм сериализации.
- **Рекомендуемое временное решение:** Не применимо.
- **Владелец решения:** Maksim Smolkov; роль решения: архитектор.
- **Контрольная точка:** Выполнено до реализации токенов.

### OQ-003. Неконсистентный пример Debt

- **Статус:** Resolved
- **Категория влияния:** `INFORMATIONAL`
- **Исходная категория:** `SAFE_DEFAULT`
- **Серьёзность:** Medium
- **Формулировка вопроса:** в полном представлении Debt пропущен третий участник или неверны `shareAmount` и данные списка?
- **Почему требуется решение:** пример с `totalAmount = 6000` содержит двух участников и долю 2000, хотя формула даёт 3000; список для того же Debt указывает трёх участников.
- **Затронутые правила или сценарии:** расчёт равной доли, чтение одного Debt, список Debt, contract-тесты frontend/backend.
- **Затронутые артефакты:** бизнес-правила, модель сущностей, HTTP-контракты.
- **Источники и связанные CONS:** CONS-003; [BR-DEBT-011](business-rules/business-rules.md#br-debt-011-расчёт-доли); [формула модели](data-model/entities.md#формула); [представление Debt](api/http-contracts.md#131-представление-долга); [список Debt](api/http-contracts.md#132-список-долгов).
- **Возможные варианты:** добавить отсутствующего участника в полное представление либо исправить `shareAmount`/`participantCount` и связанные данные примеров.
- **Рекомендуемое временное решение:** Больше не требуется; первоначально предлагалось не использовать противоречивый пример как contract-фикстуру.
- **Владелец решения:** Maksim Smolkov; роль решения: бизнес-аналитик.
- **Контрольная точка:** Выполнено до проектирования конкретного сценария.
- **Последствия откладывания:** Устранены; полное представление, создание и список теперь описывают трёх участников и долю 2000.
- **Итоговое решение:** В полное HTTP-представление добавлен отсутствовавший третий участник с уже использованным в create/update примерах `userId`. Вариант изменения доли на 3000 и `participantCount` на 2 отклонён, потому что create, update и list согласованно подтверждают состав из трёх пользователей. Изменён `docs/api/http-contracts.md`.
- **Дата и автор решения:** 2026-07-27, Codex — autonomous Block A closure.

### OQ-004. Надёжная доставка email

- **Статус:** Resolved
- **Категория влияния:** `INFORMATIONAL`
- **Серьёзность:** High
- **Вопрос:** как атомарно связать бизнес-изменение и последующую отправку email?
- **Почему требовалось решение:** транзакция PostgreSQL и публикация в RabbitMQ не образуют общую атомарную транзакцию.
- **Затронутые правила или сценарии:** регистрация, активация, сброс пароля, смена email.
- **Затронутые артефакты:** бизнес-правила, модель, ER, HTTP, ADR, Messenger.
- **Источники и связанные CONS:** CONS-004; [ADR-013](adr/architecture-decisions.md#adr-013-надёжная-доставка-email-через-transactional-outbox-и-rabbitmq).
- **Возможные варианты:** рассмотренные владельцем три варианта; принят transactional outbox с очередью.
- **Рекомендуемое временное решение:** Не применимо.
- **Владелец решения:** Maksim Smolkov; роль решения: архитектор.
- **Контрольная точка:** Выполнено до реализации email-сценариев.
- **Последствия откладывания:** риск потери email-задания после фиксации токена и последующей переделки транзакций.
- **Итоговое решение:** PostgreSQL transactional outbox → RabbitMQ → Symfony Messenger consumer → выделенный синхронный Symfony Mailer transport, семантика `at-least-once`.
- **Дата и автор решения:** 2026-07-27, Maksim Smolkov.

### OQ-005. Транзакционные границы security-команд

- **Статус:** Resolved
- **Категория влияния:** `INFORMATIONAL`
- **Исходная категория:** `SAFE_DEFAULT`
- **Серьёзность:** Medium
- **Формулировка вопроса:** какие изменения `User`, `UserSession` и использованных токенов входят в одну транзакцию для деактивации, смены и сброса пароля?
- **Почему требуется решение:** правила требуют совместного изменения security-состояния, но модель не перечисляет точный состав каждой транзакции.
- **Затронутые правила или сценарии:** деактивация, смена пароля, сброс пароля, массовый отзыв refresh-сессий.
- **Затронутые артефакты:** бизнес-правила, модель сущностей, HTTP-контракты.
- **Источники и связанные CONS:** CONS-005; [BR-USR-005](business-rules/business-rules.md#br-usr-005-деактивация); [BR-USR-007](business-rules/business-rules.md#br-usr-007-сброс-и-смена-пароля); [транзакционные границы модели](data-model/entities.md#15-транзакционные-границы); [HTTP-транзакционность](api/http-contracts.md#18-транзакционность-команд).
- **Возможные варианты:** документы не фиксируют альтернативные границы; требуется перечислить записи и изменения для каждой команды.
- **Рекомендуемое временное решение:** Принято как окончательное решение для MVP.
- **Владелец решения:** Maksim Smolkov; роль решения: архитектор.
- **Контрольная точка:** Выполнено до проектирования конкретного сценария.
- **Последствия откладывания:** Устранены; частично применённое security-состояние исключается транзакционной границей.
- **Итоговое решение:** Для деактивации, смены и сброса пароля все изменения `User`, `UserSession` и применяемого `UserActionToken` одной команды выполняются в одной транзакции PostgreSQL с блокировкой `User`, а при сбросе — также токена. Компенсационные многошаговые варианты отклонены как более сложные и допускающие промежуточное состояние. Обновлены бизнес-правила, модель и HTTP.
- **Дата и автор решения:** 2026-07-27, Codex — autonomous Block A closure.

- **Статус:** Resolved

- **Формулировка вопроса:** какой перечень CHECK-ограничений нормативен и должна ли ER полностью повторять рекомендации модели?

### OQ-015. Публичная edge-policy HTTP API

- **Статус:** Resolved
- **Категория влияния:** `BLOCKING`
- **Серьёзность:** High
- **Формулировка вопроса:** как API обрабатывает неизвестные JSON-поля, какие стабильные публичные коды получает транспортная ошибка и когда принимается клиентский `X-Request-Id`?
- **Почему требуется решение:** HTTP-контракт задаёт envelope и статусы `400/422/500`, но изначально не задавал `error.code` для malformed JSON, несовместимого типа, неподдерживаемого media type, неподдерживаемого метода и внутренней ошибки. Контракт также разрешал сохранить либо заменить клиентский request ID согласно инфраструктурной конфигурации, но конфигурация не была выбрана.
- **Затронутые правила или сценарии:** общая десериализация и validation; `POST /api/v1/auth/register` и `POST /api/v1/auth/activate`.
- **Затронутые артефакты:** HTTP-контракты, реализация HTTP infrastructure и frontend-обработка ошибок.
- **Источники и связанные решения:** [HTTP 2.1/2.4/3](api/http-contracts.md#2-общие-соглашения), [ADR-012](adr/architecture-decisions.md#adr-012-границы-и-http-соглашения-mvp).
- **Возможные варианты:**
  1. строгая граница: неизвестные поля отклоняются; каждому транспортному случаю назначается отдельный стабильный code; безопасный входящий request ID сохраняется, иначе создаётся ULID;
  2. расширяемая граница: неизвестные поля игнорируются, остальные технические коды фиксируются; безопасный входящий request ID сохраняется;
  3. минимальное поведение Symfony: оставить default extra-field policy и статусы framework, задав только общий envelope; этот вариант требует от frontend зависеть от менее точной классификации.
- **Рекомендуемое решение:** вариант 1. Он обнаруживает опечатки клиента до application-вызова, обеспечивает детерминированные frontend-коды и сохраняет полезную сквозную корреляцию без принятия произвольной строки в логи. Предлагаемая детализация: `400 INVALID_JSON` для пустого/некорректного JSON, `400 INVALID_REQUEST` для неизвестного поля, `422 VALIDATION_ERROR` с violation codes `REQUIRED`/`INVALID_TYPE`, `415 UNSUPPORTED_MEDIA_TYPE`, `405 METHOD_NOT_ALLOWED`, `500 INTERNAL_SERVER_ERROR`; входящий `X-Request-Id` принимается только при соответствии `[A-Za-z0-9._-]{1,64}`, иначе генерируется ULID.
- **Владелец решения:** Maksim Smolkov; роль решения: владелец HTTP-контракта/архитектуры.
- **Контрольная точка:** До реализации публичных DTO API.
- **Последствия откладывания:** невозможно честно отметить готовыми тесты неизвестных полей, type mismatch, media type, безопасного `500` и request correlation; молчаливый выбор станет незадокументированным публичным контрактом.
- **Дата выявления:** 2026-07-31.
- **Итоговое решение:** принят вариант 1. Неизвестные поля отклоняются как `400 INVALID_REQUEST`; пустой или malformed JSON — `400 INVALID_JSON`; missing/type/constraint violations — `422 VALIDATION_ERROR` с устойчивыми violation codes; unsupported content type — `415 UNSUPPORTED_MEDIA_TYPE`; method mismatch — `405 METHOD_NOT_ALLOWED`; непредвиденная ошибка — безопасный `500 INTERNAL_SERVER_ERROR`. Входящий `X-Request-Id` сохраняется только при соответствии `[A-Za-z0-9._-]{1,64}`, иначе сервер создаёт ULID. Варианты игнорировать extra fields и оставить framework defaults отклонены как недостаточно строгие и детерминированные для frontend.
- **Дата и автор решения:** 2026-07-31, Maksim Smolkov; вариант 1 подтверждён пользователем.

### OQ-016. Криптографический профиль непрозрачного UserActionToken

- **Статус:** Resolved
- **Категория влияния:** `BLOCKING`
- **Серьёзность:** High
- **Формулировка вопроса:** как генерируется и хэшируется непрозрачный `UserActionToken`, как версионируется формат hash и требуется ли key ring для ротации server-side ключа?
- **Почему требуется решение:** BR-SEC-003/ADR-007 требуют случайный token и хранение только `tokenHash`, но исходные документы не фиксировали entropy/encoding, keyed или unkeyed hash, формат сохранённого значения и безопасную ротацию. Молчаливый выбор является криптографическим решением и определяет возможность lookup активного token.
- **Затронутые правила или сценарии:** первичная активация, password reset, change email, token rate limit и outbox delivery.
- **Затронутые артефакты:** BR-SEC-003—005, ADR-007/013/014, HTTP `/auth/activate`, ER `UserActionToken`.
- **Возможные варианты:** (1) SHA-256 от случайного token с не менее чем 256 бит entropy и версионированным encoding; (2) HMAC-SHA-256 с versioned key ring; (3) selector + медленный password-style hash, если lookup отделяется от проверки.
- **Рекомендуемое временное решение:** Не требуется после принятия ADR-016.
- **Владелец решения:** Maksim Smolkov; роль решения: владелец security-архитектуры.
- **Контрольная точка:** До production token generation/hash lookup и реализации `POST /api/v1/auth/activate`.
- **Последствия откладывания:** Устранены; профиль генерации, versioned digest, key ring и retention key определены.
- **Дата выявления:** 2026-07-31.
- **Итоговое решение:** принят вариант 2. Публичный token содержит version prefix и 32 случайных байта; в БД хранится versioned HMAC-SHA-256 digest полного token. Key ring находится вне БД/репозитория, неизвестная версия отклоняется, старый verification key хранится минимум 31 день. Решение нормативно оформлено ADR-016.
- **Дата и автор решения:** 2026-07-31, Maksim Smolkov; вариант 2 подтверждён пользователем.

### OQ-017. Технический профиль JWT access token

- **Статус:** Resolved
- **Категория влияния:** `DEFERRED`
- **Серьёзность:** Medium
- **Формулировка вопроса:** какой signing algorithm, key management/rotation, обязательный набор claims и validation profile используются для JWT access token?
- **Почему требуется решение:** ADR-006 фиксирует JWT и TTL 15 минут, но не задаёт `alg`, `iss`, `aud`, `sub`, `iat`/`nbf`, `jti`, допустимый clock skew, `kid` и правила ротации. Без этого production authenticator потребовал бы недокументированных security-решений.
- **Затронутые правила или сценарии:** login, current user, protected commands, немедленная проверка `User.isActive`, logout/refresh и все последующие финансовые сценарии.
- **Затронутые артефакты:** ADR-006/012/014, BR-SEC-001—002, HTTP authentication contracts и будущая `UserSession` schema.
- **Возможные варианты:** асимметричный JWT с versioned key ring; симметричный HMAC JWT; замена формата новым ADR при отказе от JWT.
- **Рекомендуемое временное решение:** Не требуется после принятия ADR-017.
- **Владелец решения:** Maksim Smolkov; роль решения: владелец security-архитектуры.
- **Контрольная точка:** До `MVP-SC-002`, добавления JWT-библиотеки и production firewall/authenticator.
- **Последствия откладывания:** Устранены; signing algorithm, headers, claims, validation и key rotation определены.
- **Дата выявления:** 2026-07-31, E1-10.
- **Итоговое решение:** принят вариант 1. JWT подписывается только RS256; header содержит `typ=at+jwt` и versioned `kid`; обязательны `iss/aud/sub/iat/exp/jti`, TTL 15 минут и clock skew не более 30 секунд. JWT не содержит email или роли, а protected-команда повторно проверяет актуальный `User.isActive`. Решение нормативно оформлено ADR-017.
- **Дата и автор решения:** 2026-07-31, Maksim Smolkov; вариант 1 подтверждён пользователем.

### OQ-018. Frontend-профиль access token, session bootstrap и CSRF

- **Статус:** Resolved
- **Категория влияния:** `DEFERRED`
- **Серьёзность:** High
- **Формулировка вопроса:** где и как frontend удерживает короткоживущий JWT access token, как восстанавливает сессию после reload и какая CSRF-защита применяется к cookie-authenticated `refresh`/`logout` операциям?
- **Почему требуется решение:** ADR-006/012/017 определяют Bearer access token и rotating refresh token в `HttpOnly`, `Secure`, `SameSite=Lax` cookie, но не определяют клиентский lifecycle access token, начальный refresh, поведение нескольких вкладок и дополнительную CSRF-проверку. Молчаливый выбор `localStorage`, обычной cookie или in-memory модели изменит поверхность XSS/CSRF-рисков и пользовательское поведение.
- **Затронутые правила или сценарии:** `MVP-SC-002` login, refresh, logout, `GET /api/v1/me`, защищённые маршруты и восстановление сессии после reload.
- **Затронутые артефакты:** ADR-006/012/017, HTTP 2.3 и 8.4—8.7, модель доступа, frontend foundation и будущая `UserSession` schema.
- **Возможные варианты:**
  1. хранить access token только in-memory; после reload выполнять один cookie-authenticated refresh, затем `/me`; refresh/logout защищать проверкой same-origin `Origin`/`Sec-Fetch-Site` и отдельным CSRF-механизмом, если deployment допускает cross-site запросы;
  2. ввести BFF/session-cookie профиль, при котором браузер не получает Bearer token; требует заменяющего ADR и изменения HTTP-контрактов;
  3. хранить access token в `sessionStorage` или `localStorage`; упрощает reload/multi-tab, но делает Bearer token доступным JavaScript при XSS и требует отдельного обоснования риска.
- **Рекомендуемое временное решение:** Не требуется после принятия ADR-018.
- **Владелец решения:** Maksim Smolkov; роль решения: владелец frontend/security-архитектуры.
- **Контрольная точка:** До реализации `MVP-SC-002`, production login/refresh/current-user и первого protected route middleware.
- **Последствия откладывания:** Устранены; lifecycle access token, session bootstrap, координация refresh и CSRF-профиль определены.
- **Дата выявления:** 2026-07-31, E1-11.
- **Итоговое решение:** принят вариант 1. Access token хранится только в client-side памяти и не попадает в cookie, Web Storage, persisted store, SSR payload или логи. После reload browser выполняет single-flight refresh, сохраняет новый access token в памяти и запрашивает `/me`; protected routing ожидает окончания bootstrap. Cookie-authenticated `refresh` и `logout` используют same-origin проверки и подписанный, привязанный к refresh-сессии double-submit CSRF token. Решение нормативно оформлено ADR-018.
- **Дата и автор решения:** 2026-07-31, Maksim Smolkov; вариант 1 подтверждён пользователем.

### OQ-019. Защита password внутри idempotency request fingerprint

- **Статус:** Resolved
- **Категория влияния:** `BLOCKING`
- **Серьёзность:** High
- **Формулировка вопроса:** какой криптографический профиль и порядок ротации
  должен использовать `IdempotencyRecord.requestHash` для registration body,
  содержащего открытый password?
- **Почему требовалось решение:** прежний обычный SHA-256 canonical JSON
  детерминированно зависит от password. Утечка БД позволяет проверять варианты
  password офлайн быстрее Symfony PasswordHasher. ADR-009 требует fingerprint,
  но не определяет защиту secret-bearing полей или key rotation.
- **Затронутые правила или сценарии:** `MVP-SC-001`, BR-USR-009 и
  BR-IDEM-001—005.
- **Затронутые артефакты:** `RegisterUser`, `IdempotencyRecord`, deployment env,
  backend application/integration tests и ADR-019.
- **Возможные варианты:** versioned HMAC отдельным key ring; сохранение обычного
  SHA-256 с формальным принятием риска; иной canonicalization/secret commitment,
  сохраняющий точное сравнение всего request.
- **Рекомендуемое решение:** принять ADR-019: versioned HMAC-SHA-256
  отдельным ключом с retention не менее 24 часов. Не переиспользовать ключи
  `UserActionToken`, JWT или email payload.
- **Владелец решения:** Maksim Smolkov; роль решения: владелец
  security/архитектуры.
- **Контрольная точка:** до использования idempotency fingerprint для запросов,
  содержащих пользовательский password.
- **Последствия откладывания:** устранены; новые fingerprint защищены HMAC, а
  переходная совместимость ограничена TTL старых записей.
- **Дата выявления:** 2026-08-02.
- **Связанное решение:** [ADR-019](adr/architecture-decisions.md#adr-019-криптографический-профиль-idempotency-fingerprint-для-secret-bearing-команд), статус `Accepted`.
- **Итоговое решение:** принят versioned HMAC-SHA-256 с отдельным key ring.
  Старые SHA-256 записи поддерживаются только в течение оставшейся части их
  24-часового окна; новые и перезапущенные записи используют HMAC.
- **Дата и автор решения:** 2026-08-02, Maksim Smolkov; вариант 1 подтверждён
  пользователем.

### OQ-020. Нормативный `UserSession.revokedAt` CHECK и terminal state

- **Статус:** Resolved
- **Категория влияния:** `BLOCKING_AUTH_IMPLEMENTATION`
- **Серьёзность:** Medium
- **Формулировка вопроса:** требуется ли для `UserSession` дополнительный
  нормативный CHECK constraint или terminal-state rule, связанный с
  `revokedAt`, помимо явно зафиксированного `expiresAt > createdAt`?
- **Почему требуется решение:** `DR-E1-004` формулирует задачу как CHECK для
  времён и terminal state согласно ER-модели, но ER-модель и перечень
  рекомендуемых ограничений БД для `UserSession` явно фиксируют
  `CHECK(expiresAt > createdAt)` и индексы по пользователю, сроку и отзыву.
  Дополнительное правило для `revokedAt` нельзя вывести однозначно без
  изменения нормативных документов.
- **Затронутые правила или сценарии:** `MVP-SC-002`, `UserSession`, refresh
  rotation, logout/logout-all и security changes следующих этапов.
- **Затронутые артефакты:** data model, ER diagram, business rules,
  HTTP contracts, development roadmap, future migration.
- **Источники и связанные CONS:** CONS-020; [`UserSession`](data-model/entities.md#9-usersession);
  [рекомендуемые ограничения БД](data-model/entities.md#14-рекомендуемые-ограничения-бд);
  [ER локальные CHECK](data-model/er-diagram.md#7-локальные-check-ограничения);
  [`DR-E1-004`](development-roadmap.md#53-data-и-migration).
- **Возможные варианты:** оставить только `expiresAt > createdAt`; добавить
  `revokedAt IS NULL OR revokedAt >= createdAt`; добавить другой terminal-state
  rule; явно подтвердить, что terminal state проверяется только доменным слоем.
- **Рекомендуемое временное решение:** для этапа реализации migration добавлять
  только нормативный `CHECK(expiresAt > createdAt)`; дополнительный
  `revokedAt`/terminal-state CHECK не добавлять до решения.
- **Владелец решения:** Maksim Smolkov; роль решения: владелец
  security/архитектуры.
- **Контрольная точка:** до `DR-E1-002—005` и первой migration
  `user_session`.
- **Последствия откладывания:** migration может закрепить лишнее или неверное
  ограничение, которое затем придётся менять вместе с моделью и тестами.
- **Дата выявления:** 2026-08-08, `MVP-SC-002` contract audit.
- **Итоговое решение:** принят вариант 4. Для `UserSession` не вводится
  дополнительный DB CHECK по `revokedAt` и не вводится отдельный DB-level
  terminal-state constraint. Нормативный CHECK остаётся
  `expiresAt > createdAt`. Terminal state определяется доменным lifecycle:
  refresh-сессия недействительна, если `revokedAt IS NOT NULL` или
  `expiresAt <= now`; эти переходы и проверки выполняются приложением внутри
  транзакции с блокировкой строки сессии там, где это требуется refresh
  lifecycle.
- **Дата и автор решения:** 2026-08-08, Maksim Smolkov; вариант 4 подтверждён
  пользователем.

### OQ-021. Публичный результат повторного запроса активации

- **Статус:** Resolved
- **Категория влияния:** `BLOCKING_CONTRACT`
- **Серьёзность:** High
- **Формулировка вопроса:** должен ли
  `POST /api/v1/auth/activation-requests` раскрывать неверные учётные данные
  или уже активный аккаунт через `401 INVALID_CREDENTIALS` и
  `409 ACCOUNT_ALREADY_ACTIVE`, либо возвращать единый публичный результат?
- **Почему требовалось решение:** HTTP 8.2 требовал разные ответы для
  неверных credentials и активного аккаунта, тогда как roadmap этапа 6 требовал
  одинаковый `202` и отсутствие account enumeration. Оба поведения нельзя
  реализовать одновременно.
- **Затронутые правила или сценарии:** `MVP-SC-001`, BR-USR-002/006,
  BR-SEC-003—007 и этап 6A.
- **Затронутые артефакты:** HTTP 8.2 и 17, development roadmap 10.3,
  будущие backend/frontend implementation и тесты.
- **Возможные варианты:** сохранить разные `401`/`409`; возвращать единый
  `202` для каждого синтаксически корректного тела при обязательной внутренней
  проверке email и password; разделить initial resend и reactivation на разные
  endpoints с расширением модели состояния аккаунта.
- **Итоговое решение:** принят вариант 2. Endpoint принимает `email` и
  `password`, но для каждого синтаксически корректного тела возвращает
  одинаковый `202 activation_email_scheduled`. Новый `ACTIVATE_ACCOUNT` и
  durable email intent создаются только для существующего неактивного
  пользователя с верным паролем. Неизвестный email, неверный пароль и активный
  аккаунт не создают token/outbox и не имеют отдельного публичного результата.
  `422` остаётся для синтаксической валидации, `429` — для rate limit.
- **Дата и автор решения:** 2026-09-27, Maksim Smolkov; вариант 2 подтверждён
  пользователем.

### OQ-022. Публичные ошибки и cookie clearing для logout

- **Статус:** Resolved
- **Категория влияния:** `BLOCKING_CONTRACT`
- **Серьёзность:** High
- **Формулировка вопроса:** какой public result должен возвращать current

  already-revoked refresh token; должны ли refresh/CSRF cookies очищаться при
  `403 FORBIDDEN`; и должен ли Bearer-authenticated logout-all очищать auth
  cookies текущего browser?
- **Почему требуется решение:** HTTP 8.6 однозначно задаёт `204` без refresh
  cookie, `403` для failed same-origin/CSRF и clear-cookie headers для success,
  но не задаёт ветки unusable presented token или headers при `403`. HTTP 8.7
  задаёт только `204` и revoke всех sessions без `Set-Cookie`. ADR-018 требует
  очистить обе cookies для logout и завершить local session, но не устраняет
  эти различия. Самостоятельный выбор изменит публичный security contract,
  возможность повторного запроса и browser state.
- **Затронутые правила или сценарии:** `MVP-SC-003`, HTTP 2.3/8.6—8.7,
  ADR-018, current logout, logout-all, safe errors и browser E2E.
- **Затронутые артефакты:** HTTP contracts, feature spec, backend controller,
  request guard, cookie factory, frontend lifecycle и тесты.
- **Источники:** [HTTP 8.6—8.7](api/http-contracts.md#86-выход-из-текущей-сессии),
  [ADR-018](adr/architecture-decisions.md#adr-018-frontend-lifecycle-access-token-session-bootstrap-и-csrf),
  [`MVP-SC-003`](mvp-scope.md#mvp-sc-003),
  [logout feature audit](features/logout-session-revocation.md).
- **Возможные варианты:**
  1. после успешного request guard всегда отвечать `204` и очищать cookies,
     включая unusable token; при `403` cookies не менять; logout-all очищает
     cookies текущего browser;
  2. unusable token возвращает `401 INVALID_REFRESH_TOKEN`, `403` не очищает
     cookies, logout-all не управляет cookies;
  3. разделить known terminal session (`204`) и malformed/unknown/rotated token
     (`401`), отдельно определить clearing для каждой ошибки и logout-all.
- **Рекомендуемый вариант для решения:** вариант 1 минимизирует раскрытие
  session presence и делает user intent безопасно повторяемым, но должен быть
  явно принят. Для failed CSRF cookies рекомендуется не менять, чтобы
  forbidden request не создавал logout side effect; logout-all рекомендуется
  очищать cookies текущего browser вместе с `204`.
- **Владелец решения:** Maksim Smolkov; роль решения: владелец
  security/архитектуры.
- **Контрольная точка:** до `SC3-02/04` и HTTP/component test implementation.
- **Последствия откладывания:** нельзя зафиксировать exact controller branches,
  clear-cookie tests, retry behavior и browser reload result.
- **Дата выявления:** 2026-09-30, `SC3-01` contract audit.
- **Итоговое решение:** для unusable refresh credential принят вариант 1:
  после request-level Origin/Fetch Metadata и header/cookie equality checks
  current logout возвращает единый `204`, очищает обе cookies и не выполняет
  DB mutation. Для найденной session signature и session binding CSRF остаются
  обязательными. При любом `403 FORBIDDEN` cookies не изменяются. Успешный
  logout-all возвращает `204` и сразу очищает refresh- и CSRF-cookies текущего
  browser; Bearer authentication failure cookies не меняет.
- **Дата и автор решения:** 2026-09-30, Maksim Smolkov; варианты подтверждены
  пользователем.

<a id="oq-023"></a>

### OQ-023. Гарантия current logout при гонке с refresh rotation

- **Статус:** Resolved
- **Категория влияния:** `BLOCKING_AUTH_CONCURRENCY`
- **Серьёзность:** High
- **Формулировка вопроса:** какую серверную гарантию обязан давать current
  logout, если refresh той же session первым блокирует строку и заменяет
  `refreshTokenHash`, а concurrent logout уже предъявил старый token?
- **Почему требуется решение:** текущая session находится только по mutable
  refresh hash. Если refresh wins, повторный `SELECT ... WHERE old_hash FOR
  UPDATE` может не найти row после re-evaluation, поэтому logout не может
  отозвать уже rotated session. Web Locks предотвращает гонку для compliant
  вкладок одного browser profile, но не является серверной гарантией и не
  покрывает direct clients или response reordering. Документы требуют описать
  refresh-vs-logout race, но не задают stable session locator или winner rule.
- **Затронутые правила или сценарии:** `MVP-SC-003`, BR-SEC-002, HTTP 8.5—8.6,
  ADR-018, session revocation и concurrency acceptance.
- **Затронутые артефакты:** refresh token profile, application port,
  `DoctrineUserSessionRepository`, frontend Web Lock flow и race tests.
- **Источники:** [`UserSession`](data-model/entities.md#9-usersession),
  [HTTP 8.5—8.6](api/http-contracts.md#85-обновление-сессии),
  [ADR-018](adr/architecture-decisions.md#adr-018-frontend-lifecycle-access-token-session-bootstrap-и-csrf),
  фактические `RefreshTokenCodec`, `RefreshSession` и session repository.
- **Возможные варианты:**
  1. считать Web Lock обязательной client guarantee: refresh winner допустим,
     direct concurrent logout по старому token может стать no-op `204`;
  2. ввести stable session locator в refresh credential/token profile и
     блокировать row по нему до проверки текущего hash; оценить совместимость
     уже выданных tokens, migration при этом может не требоваться;
  3. хранить ограниченную историю предыдущего hash или иной server-side alias;
     это расширяет модель, retention и attack surface;
  4. определить bounded retry/coordination protocol, при котором logout после
     refresh winner повторяется с новыми browser cookies; direct-client
     гарантия остаётся ограниченной.
- **Рекомендуемое временное решение:** production implementation current
  logout не начинать до выбора. Независимо от варианта frontend должен брать
  тот же Web Lock и читать cookies только после lock; JWT blacklist и global
  session version не вводить.
- **Владелец решения:** Maksim Smolkov; роль решения: владелец
  security/архитектуры.
- **Контрольная точка:** до `SC3-02` и `SC3-07`.
- **Последствия откладывания:** невозможно написать честный concurrency test и
  доказать, что успешный logout не оставляет usable rotated refresh session.
- **Дата выявления:** 2026-09-30, `SC3-01` contract audit.
- **Итоговое решение:** принят вариант 2. Новый versioned refresh credential
  содержит stable `UserSession.id` locator и 32 random bytes; в БД хранится
  только hash полного credential. Refresh блокирует row по locator и требует
  exact current-hash match. Current logout блокирует ту же row по locator и при
  valid session-bound CSRF отзывает её даже для stale rotated credential.
  Production-сессий прежнего формата нет, поэтому legacy compatibility не
  вводится; прежние local/test cookies становятся недействительными. Схема БД
  уже содержит PK session, migration не требуется.
- **Дата и автор решения:** 2026-09-30, Maksim Smolkov; вариант 2 подтверждён
  пользователем.

### OQ-024. Frontend UX для logout и logout-all

- **Статус:** Resolved
- **Категория влияния:** `BLOCKING_FRONTEND_CONTRACT`
- **Серьёзность:** High
- **Формулировка вопроса:** требуется ли confirmation для logout-all, куда
  redirect-ить после success и safe error, и как показывать состояние, когда
  local auth очищен, но server revoke не подтверждён из-за transport/`403`/`5xx`?
- **Почему требуется решение:** ADR-018 однозначно требует очистить local token
  и current user и рассылать событие только после успешного server logout, но
  не определяет UI location, confirmation или recovery copy. Немедленный
  redirect на существующую login page может вызвать bootstrap; при сохранённых
  cookies это способно восстановить session после неуспешного logout и создать
  противоречивый UX.
- **Затронутые правила или сценарии:** `MVP-SC-003`, ADR-018, auth middleware,
  login page bootstrap, межвкладочное завершение и accessibility.
- **Затронутые артефакты:** `$auth` API, current-user state, protected page,
  auth middleware, login page, component и browser E2E tests.
- **Источники:** [ADR-018](adr/architecture-decisions.md#adr-018-frontend-lifecycle-access-token-session-bootstrap-и-csrf),
  [frontend foundation](frontend-foundation.md#7-состояние-текущего-пользователя),
  [logout feature audit](features/logout-session-revocation.md).
- **Возможные варианты:**
  1. current logout без confirmation, logout-all с confirmation; success
     redirect на `/login` в explicit signed-out mode, error остаётся на
     dedicated result state с явным retry и suppressed bootstrap;
  2. обе команды без confirmation и всегда redirect на `/login`, расширив
     login bootstrap guard для failed logout;
  3. confirmation для обеих команд и inline result на защищённой странице до
     явного перехода пользователя.
- **Рекомендуемый вариант для решения:** вариант 1 различает обычный и
  destructive mass logout, не маскирует server failure и предотвращает
  automatic restoration/redirect loop. Реализация должна оставаться доступной
  с клавиатуры и не передавать token в route/query/storage.
- **Владелец решения:** Maksim Smolkov; роль решения: Product Owner совместно с
  владельцем frontend/security.
- **Контрольная точка:** до `SC3-05` и frontend acceptance tests.
- **Последствия откладывания:** нельзя зафиксировать component states, redirect
  assertions, confirmation copy и recovery behavior.
- **Дата выявления:** 2026-09-30, `SC3-01` contract audit.
- **Итоговое решение:** принят вариант 1. Current logout выполняется без
  confirmation; logout-all требует явного confirmation. После подтверждённого
  server `204` frontend очищает local auth state, рассылает token-free
  `session-ended` и переходит на `/login` в explicit signed-out mode без
  bootstrap. После transport/`403`/`5xx` local state очищается, success event
  не рассылается, автоматический bootstrap запрещён, а dedicated safe-error
  state сообщает, что server revoke не подтверждён, и предлагает явный retry.
- **Дата и автор решения:** 2026-09-30, Maksim Smolkov; вариант 1 и
  confirmation только для logout-all подтверждены пользователем.
