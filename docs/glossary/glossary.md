## Назначение

**Статус:** финальная согласованная версия этапа проектирования.


Документ фиксирует единый язык предметной области Equo. Эти термины должны одинаково использоваться в бизнес-правилах, коде, HTTP-контрактах, тестах, интерфейсе и архитектурной документации.

Equo — приложение для учёта долгов и взаиморасчётов между пользователями. В MVP поддерживается одна валюта — EUR. Все денежные значения хранятся в целых евроцентах.

## Пользователь и аккаунт

### Пользователь (`User`)

Зарегистрированный аккаунт Equo.

Пользователь может быть активным или неактивным. Отдельного признака подтверждения email нет.

### Активный пользователь

Пользователь с `isActive = true`.

Он может:

- авторизоваться;
- создавать долги и ручные трансферы;
- участвовать в новых долгах;
- создавать и принимать коннекты;
- изменять профиль;
- деактивировать аккаунт.

### Неактивный пользователь

Пользователь с `isActive = false`.

Это может означать:

1. аккаунт только зарегистрирован и ещё не активирован через email;
2. пользователь ранее самостоятельно деактивировал аккаунт.

Неактивный пользователь:

- не может авторизоваться;
- не может участвовать в новых финансовых операциях;
- не может создавать или принимать новые коннекты;
- остаётся видимым в существующих коннектах;
- сохраняет существующие долги, трансферы и балансы.

Для повторной активации пользователь подтверждает email и пароль, после чего получает одноразовую ссылку активации.

### Активация аккаунта

Переход `User.isActive` из `false` в `true` по одноразовой ссылке.

Один и тот же процесс используется:

- после регистрации;
- после добровольной деактивации.

После активации пользователь входит вручную. Автоматическая авторизация по ссылке не выполняется.

### Деактивация аккаунта

Добровольное отключение аккаунта после повторного ввода пароля.

Деактивация:

- устанавливает `isActive = false`;
- отзывает активные сессии;
- не удаляет финансовые данные;
- блокирует новые операции до повторной активации.

## Коннекты

### Коннект (`Connect`)

Постоянная неориентированная связь между двумя пользователями.

Коннект:

- не имеет направления;
- существует в единственном экземпляре для одной пары;
- не может связывать пользователя с самим собой;
- не удаляется и не отменяется;
- объединяет общую историю трансферов и взаимный баланс.

Коннект создаётся:

- после принятия приглашения;
- автоматически при создании доли долга;
- вручную между активными пользователями, участвующими в одном доступном долге.

### Стороны коннекта

Два пользователя, связанные одним `Connect`.

Каждый трансфер коннекта обязательно направлен от одной стороны к другой. Поэтому сторона коннекта всегда является либо отправителем, либо получателем любого его трансфера.

### Доступный пользователь для финансовой команды

Активный пользователь, которого текущий пользователь вправе выбрать плательщиком или участником нового долга. Доступными считаются:

- сам текущий пользователь;
- активная сторона существующего `Connect`;
- текущий соучастник с активным аккаунтом долга, доступного текущему пользователю.

Общий поиск произвольных пользователей в MVP отсутствует.

### Приглашение в коннект (`ConnectInvitation`)

Одноразовая ссылка для создания коннекта с автором приглашения.

Для одного пользователя существует не более одного действующего неиспользованного приглашения. Повторный запрос возвращает существующее приглашение, пока оно действительно.

Отзыв приглашения в MVP не предусмотрен.

## Долг и разделение

### Долг (`Debt`)

Групповая операция, описывающая разделение общей суммы между плательщиком и участниками.

Долг содержит:

- название;
- описание;
- общую сумму;
- одного плательщика;
- автора;
- состав участников;
- версию;
- признак мягкого удаления.

Сам `Debt` не влияет на баланс. На баланс влияют только созданные по нему автоматические трансферы.

### Автор долга

Пользователь, создавший долг.

Автор:

- может отличаться от плательщика;
- обязан быть плательщиком или участником разделения;
- единственный может редактировать и удалять долг;
- не может исключить себя из состава, если не является плательщиком.

Если автор деактивирован, долг замораживается.

### Плательщик (`payer`)

Пользователь, оплативший общую сумму.

В MVP у долга ровно один плательщик. После создания его нельзя изменить.

Если плательщик деактивирован, долг нельзя редактировать или удалять.

### Участник долга (`DebtParticipant`)

Связь пользователя с долгом.

**Текущий участник** — запись `DebtParticipant` с `isDeleted = false`. Это состояние участия не следует путать с активностью аккаунта `User.isActive`: текущий участник может позднее деактивировать аккаунт и при этом остаться в составе долга.

**Исключённый участник** — запись `DebtParticipant` с `isDeleted = true`. Запись сохраняется и может быть восстановлена после реактивации пользователя.

Плательщик тоже может быть текущим участником разделения, но автоматический трансфер самому себе не создаётся.

### Состав долга

Набор записей `DebtParticipant` с `isDeleted = false`, между которыми делится сумма.

Состав определяет:

- размер доли;
- набор автоматических трансферов;
- право чтения активного долга.

После удаления из состава пользователь теряет доступ к карточке долга, но продолжает видеть собственные трансферы.

### Включение плательщика в разделение

Если плательщик включён:

- он учитывается в числе участников;
- несёт собственную долю;
- self-transfer не создаётся.

Если исключён, сумма делится только между остальными участниками.

### Общая сумма (`totalAmount`)

Исходная сумма расхода в евроцентах.

Она:

- положительна;
- хранится в `Debt`;
- используется для пересчёта;
- напрямую не участвует в балансе.

### Доля

Сумма, рассчитанная сервером для одного участника.

Формула MVP:

`shareAmount = ceil(totalAmount / participantCount)`

`participantCount` включает всех пользователей в разделении, в том числе плательщика, если он включён.

Из-за округления вверх сумма математических долей может быть немного больше `totalAmount`. Это осознанное правило MVP.

## Трансферы и баланс

### Трансфер (`Transfer`)

Направленная финансовая запись между двумя сторонами одного коннекта.

Только активные трансферы влияют на баланс.

### Отправитель (`sender`)

Сторона, от которой направлено финансовое обязательство.

### Получатель (`receiver`)

Сторона, в пользу которой направлено финансовое обязательство.

### Автоматический трансфер доли (`DEBT_SHARE`)

Трансфер, создаваемый системой по участнику долга.

Направление:

`плательщик → участник`

Экономический смысл: участник должен плательщику рассчитанную долю.

Особенности:

- управляется только через `Debt`;
- напрямую не редактируется;
- для плательщика не создаётся;
- для одного текущего участника существует не более одного;
- при исключении участника перестаёт влиять на баланс;
- может быть восстановлен при повторном добавлении.

### Ручной трансфер (`MANUAL`)

Трансфер, созданный пользователем вручную.

Используется для:

- возврата денег;
- передачи денег;
- корректировки баланса;
- других двусторонних финансовых операций.

Ручной трансфер:

- создаётся любой активной стороной коннекта;
- может иметь любое направление;
- может превышать текущий долг;
- может изменить знак баланса;
- редактируется и удаляется только автором;
- виден обеим сторонам.

### Автор трансфера

Пользователь, создавший ручной трансфер.

Автор влияет на право изменения, но не на видимость.

Для `MANUAL` поле `createdById` обязательно. Для `DEBT_SHARE` оно равно `null`, поскольку автоматический трансфер создаётся системой и управляется только через долг.

### Связанный трансфер (`relatedTransfer`)

Необязательная информационная ссылка ручного трансфера на `DEBT_SHARE`.

Связь:

- не означает погашение;
- не влияет на баланс;
- не ограничивает сумму;
- допустима только внутри одного коннекта;
- при создании или замене может указывать только на неудалённый `DEBT_SHARE`;
- неизменённая историческая ссылка может сохраняться при редактировании других полей, даже если связанный `DEBT_SHARE` позднее мягко удалён;
- ссылку можно очистить.

### Погашение

Бизнес-смысл ручного трансфера, уменьшающего задолженность.

Отдельной сущности или статуса погашения нет.

### Баланс коннекта

Сумма всех активных трансферов между двумя пользователями.

Для направления `A → B`:

`balance(A, B) = sum(active A → B) - sum(active B → A)`

Интерпретация:

- положительное значение — `B` должен `A`;
- отрицательное — `A` должен `B`;
- ноль — обязательства уравновешены.

Баланс вычисляется по трансферам и не является самостоятельным источником истины.

### Переплата

Ситуация, когда ручной трансфер превышает текущую задолженность и меняет знак баланса.

Переплата разрешена.

### История трансферов

Полный список трансферов одного коннекта.

Обе стороны видят:

- ручные и автоматические трансферы;
- мягко удалённые ручные трансферы;
- мягко удалённые `DEBT_SHARE`, в том числе после исключения участника или удаления долга;
- сумму и направление;
- автора;
- доступную связь с долгом.

## Удаление и заморозка

### Мягкое удаление

Запись остаётся в базе, но исключается из активного поведения.

Используется для:

- `Debt`;
- `DebtParticipant`;
- `Transfer`.

### Удалённый долг

Долг с `isDeleted = true`.

Он:

- не показывается в обычном списке;
- не имеет отдельного архива в MVP;
- может открываться по прямой ссылке или из трансфера;
- доступен только для чтения;
- не восстанавливается;
- не влияет на баланс через свои `DEBT_SHARE`.

Доступ сохраняется у автора, плательщика и пользователей, входивших в текущий состав (`DebtParticipant.isDeleted = false`) на момент удаления, независимо от их `User.isActive`. Пока аккаунт неактивен, пользователь не может войти; после реактивации право чтения сохраняется.

### Удалённый участник

`DebtParticipant` с `isDeleted = true`.

Он:

- не участвует в расчёте;
- не имеет доступа к активному долгу;
- сохраняется для целостности;
- может быть восстановлен, если пользователь активен.

### Удалённый трансфер

Трансфер с `isDeleted = true`. Он не влияет на баланс и остаётся видимым обеим сторонам коннекта.

Удалённый ручной трансфер не редактируется и не восстанавливается в MVP. Автоматический `DEBT_SHARE` может быть восстановлен только через повторное добавление соответствующего участника в неудалённый долг.

### Замороженный долг

Активный долг, который нельзя изменить.

Причины:

- автор неактивен;
- плательщик неактивен.

Неактивность обычного участника сама по себе долг не замораживает.

### Замороженный ручной трансфер

Трансфер, который нельзя изменить или удалить, потому что отправитель или получатель неактивен.

## Доступ и права

### Право чтения долга

Активный долг доступен:

- автору;
- плательщику;
- текущему участнику.

После удаления из состава доступ прекращается.

### Право управления долгом

Только автор, если:

- долг не удалён;
- автор активен;
- плательщик активен;
- версия совпадает.

### Право чтения трансфера

Любая сторона соответствующего коннекта.

Доступ к трансферу и связанному долгу проверяются отдельно.

### Право изменения ручного трансфера

Только автор, если:

- трансфер не удалён;
- обе стороны активны;
- версия совпадает.

### Сервер как источник истины

Клиент передаёт намерение, а сервер:

- проверяет права;
- рассчитывает доли;
- создаёт трансферы;
- вычисляет баланс;
- контролирует целостность.

## Согласованность

### Версия (`version`)

Целое число для оптимистической блокировки.

Хранится у:

- `Debt`;
- `Transfer`.

Правила:

- при создании `version = 1`;
- успешное изменение увеличивает версию;
- клиент передаёт ожидаемое значение;
- несовпадение приводит к конфликту без частичного сохранения.

### Оптимистическая блокировка

Защита от параллельного редактирования.

Изменения участников и `DEBT_SHARE` защищаются версией агрегата `Debt`.

### Атомарная операция

Операция сохраняется полностью или не сохраняется вовсе.

Например, изменение долга одной транзакцией обновляет сам долг, участников, коннекты, автоматические трансферы и версию.

### Идемпотентность

Повтор одного запроса не создаёт дубликат.

Для команд создания используется `Idempotency-Key`.

Одинаковые ключ и тело возвращают исходный результат. Тот же ключ с другим телом вызывает конфликт.

### `Idempotency-Key`

Уникальный идентификатор клиентской попытки, обычно UUID.

## Безопасность аккаунта

### Пароль

Секрет пользователя для входа, деактивации, реактивации и подтверждения чувствительных операций.

Единая политика MVP:

- от 12 до 128 Unicode code points;
- хотя бы один символ не является пробельным;
- значение не обрезается и не нормализуется;
- требования к обязательным классам символов отсутствуют;
- открытый пароль не хранится и не журналируется.

Одинаковая политика применяется при регистрации, смене и сбросе пароля. Backend является источником истины для проверки.

### Пользовательская сессия (`UserSession`)

Серверная запись, связанная с refresh-токеном.

Позволяет:

- обновлять access-токен;
- выйти с одного устройства;
- отозвать одну или все refresh-сессии;
- запретить выпуск новых access-токенов после выхода, смены пароля или деактивации.

### Access-токен

Короткоживущий токен API.

Защищённые команды дополнительно проверяют текущее `User.isActive`.

### Refresh-токен

Долгоживущий ротируемый токен. В базе хранится только его хэш. Выход, смена или сброс пароля отзывают соответствующие refresh-сессии. Уже выданный короткоживущий access-токен может технически действовать до своего `exp`; деактивация блокирует защищённые команды немедленно благодаря проверке `User.isActive`.

### Токен пользовательского действия (`UserActionToken`)

Одноразовый email-токен для:

- `ACTIVATE_ACCOUNT`;
- `RESET_PASSWORD`;
- `CHANGE_EMAIL`.

В публичной ссылке находится случайное значение. В базе хранится только его хэш.

Для `CHANGE_EMAIL` сервер хранит в `payload` подтверждаемый новый адрес. Email не является частью публичного токена.

Для одного пользователя и одного `purpose` существует не более одного незавершённого токена (`usedAt IS NULL` и `invalidatedAt IS NULL`). Новая выдача сериализуется блокировкой пользователя, аннулирует прежний незавершённый токен того же назначения и создаёт новый в одной транзакции.

### Назначение токена (`purpose`)

Тип действия. Токен нельзя применить для другого назначения.

### Полезная нагрузка (`payload`)

Необязательные серверные данные.

Для смены email:

```json
{
  "newEmail": "new@example.com"
}
```

### Сброс пароля

Изменение пароля через `RESET_PASSWORD`.

Сброс:

- отзывает все refresh-сессии;
- не активирует неактивный аккаунт;
- не гарантирует мгновенное прекращение уже выданного access-токена до его `exp`.

### Смена email

Новый адрес становится основным только после подтверждения. До этого используется старый.

## Архитектурные термины

### Агрегат долга

`Debt` вместе с `DebtParticipant` и автоматическими `DEBT_SHARE`, изменяемыми согласованно.

### Команда

Операция изменения состояния, например `CreateDebt` или `DeactivateAccount`.

### Запрос (`query`)

Операция чтения без изменения состояния.

### Инвариант

Правило, которое должно оставаться истинным после каждой успешной операции.

### Инфраструктурная сущность

Техническая запись, не являющаяся самостоятельным финансовым понятием:

- `UserSession`;
- `UserActionToken`;
- `IdempotencyRecord`;
- `EmailDeliveryOutbox`.

### Transactional outbox

Способ атомарно сохранить бизнес-изменение и намерение отправить внешнее сообщение в одной транзакции PostgreSQL. Отдельный relay позднее публикует сохранённое задание в RabbitMQ.

### Задание доставки email (`EmailDeliveryOutbox`)

Инфраструктурная запись для надёжной доставки письма, связанного с `UserActionToken`. Содержит стабильный `deliveryId`, адрес получателя, ключ шаблона, временно зашифрованный payload и состояние обработки.

### Durable intent

Зафиксированное в PostgreSQL намерение выполнить доставку. После успешного commit задание не теряется при временной недоступности RabbitMQ или SMTP и может быть повторено.

### Семантика `at-least-once`

Каждое задание обрабатывается как минимум один раз, пока не завершится успешно или не перейдёт в окончательный отказ. Повторная обработка допустима, поэтому relay и consumer используют `deliveryId` для дедупликации и должны быть идемпотентными.

## Деньги

### Валюта MVP

EUR.

Отдельное поле валюты пока не требуется.

### Евроцент

Минимальная единица хранения:

- `100` = `1,00 EUR`;
- `1250` = `12,50 EUR`.

`float` и `double` для денег не используются.

## Термины, не используемые в MVP

- дружба — используется `Connect`;
- статус долга `open/paid/closed`;
- автоматическое погашение;
- остаток конкретного долга;
- отмена коннекта;
- восстановление удалённого ручного трансфера.
